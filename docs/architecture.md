## 端口约定

| 端口 | 谁在用 | 说明 |
|---|---|---|
| 8787 | 简传 Lite 电脑端 | 可在 `--port` 或 `data/config.json` 改 |
| 8788 | 简传 Lite 手机端 | 手机当前台服务端时监听，供别的设备访问 |
| 8848 | MediaShare | 媒体库；`config.json` 的 `port` 可改 |

## 两端互认的“指纹”

投影仪/电视端靠指纹区分两种源，而不是猜端口：

- **MediaShare**：`GET /api/list?path=` 返回的 JSON 里有 `entries` 和 `path`
- **简传 Lite**：`GET /api/alive` 返回里有 `jianchuan-lite`（旧版回退看 `ok` + `ips`）

## 电视页契约（手机 → 播放器）

手机端的 `/tv` 是给电视用的网页，播放器外壳（WebView）和它有四个约定：

1. UA 末尾追加 ` TV`，网页据此切到电视布局
2. 网页点播时跳转 `/play?path=<相对路径>&title=<标题>`
3. 外壳把 `/play` 拦下来，交给原生播放器，URL 拼成 `http://host:port/media/<相对路径>`
4. 播放器自己再请求 `/api/episodes`（同目录选集）和 `/api/progress`（进度读写）；
   返回键调 `window.__tvGoUp()`，网页返回 `true` 表示“我自己回上一级了”

`rel = 文件绝对路径去掉前导斜杠`；服务端收到时不要再 url-decode 一次
（nanohttpd 已经解码过）。

## 进度存哪

- 手机端：`filesDir/tv_progress.json`，key 是相对路径，先写 `.tmp` 再 rename
- MediaShare：`progress.json`，同样是相对路径
- 播放器：写入对端（谁提供的片源就写谁），所以换设备能接着看

## 为什么电脑端用 Python、播放器用 libVLC

- 电脑端要的是“能跑、能打包、零依赖”：Python 标准库起一个 HTTP 服务就够，
  `pywebview` 只是可选的窗口壳。实测下载 879 MB/s、上传 ~1 GB/s，
  在 Wi-Fi 40–80 MB/s 的现实中完全不是瓶颈。
- 播放器要的是“什么都能解”：老投影仪自带浏览器只有 Chrome 66，`<video>` 播 1080p
  直接 `MEDIA_ERR_DECODE`；系统硬解码器也坏。libVLC 软解最稳。
  注意 4K HEVC 仍建议 `--avcodec-hw=mediacodec` 走硬解（实测 CPU 7%），
  但压制组把 1080p 错标 `level=5.0` 时硬解会黑屏，要么重编码到 4.1，要么软解。
